# Markdown Good Practices

This guide outlines best practices for writing and organizing VitePress Markdown documentation so it is clear, consistent, accessible, and easy to maintain.

## File and Directory Structure

A well-organized file structure keeps the documentation navigable and aligned with VitePress routing.

### `index.md` at Every Directory Root

Every section or module directory under `docs/` should contain an `index.md` file acting as the landing page and summary for that directory.

::: warning
VitePress excludes `**/README.md` and `**/TODO.md` via `srcExclude` in `.vitepress/config.ts`. Do not name published pages or directory indexes `README.md`—always use `index.md`.
:::

### File Naming Conventions

Consistent file naming makes pages predictable and URLs clean:

- **Use lowercase:** `file-name.md` instead of `FileName.md` or `File-Name.md`.
- **Use hyphens for separators:** Use `kebab-case` for multi-word file names (e.g., `getting-started.md`).
- **Be descriptive:** File names should clearly indicate their content (e.g., `api-reference.md`, `creating-a-new-survey.md`).

### Asset Location

Store images, diagrams, and screenshots locally next to the pages that reference them:

- **Create an `assets/` directory** inside the folder containing your Markdown files (or `assets/<guide-name>/` for multi-step guides).
- **Use relative paths** (e.g., `./assets/feature-a/step-1.png`) so `pnpm check:docs-links` and VitePress can verify every asset.
- **Do not hand-edit `*-auto.png` files**—they are generated by Playwright specs under `documentation/src/`.

#### Example Directory Structure

```text
docs/app/example/how-to/
├── index.md
├── REF.md
├── assets/
│   └── feature-a/
│       └── step-1.png
└── feature-a.md
```

In `feature-a.md`, reference the image with a relative path:

```markdown
![Diagram for Feature A](./assets/feature-a/step-1.png)
```

### Traceability (`REF.md`)

Maintain a `REF.md` file next to each docs folder mapping published pages back to the source files they document in `accessibleData`. Write each source as a **backticked repo-relative path** (e.g. `` `app/app-survey/src/page/edit/design/behavior.ts` ``), never a Markdown link: VitePress reads a relative `.md` link as a page and fails the build, and `pnpm check:docs-links` rejects a docs link that leaves `docs/`.

## Content Best Practices

- **Structure with Headings:** Use headings (`#`, `##`, `###`) in logical order without skipping levels.
- **Keep it Concise:** Write clear, direct sentences. Use lists and tables to present structured information.
- **Use Code Blocks:** Use fenced code blocks with language identifiers for syntax highlighting.
- **Link Generously:** Cross-link related tutorials, how-to guides, references, and explanations using relative Markdown links.
- **US English:** Use consistent American English spelling (e.g., *customize*, *behavior*, *color*, *organization*, *localization*).
- **Disability Terminology (UN CRPD):** Align copy with the UN Convention on the Rights of Persons with Disabilities (`comms/foundations/convention-on-the-rights-of-persons-with-disabilities.md`). Use person-first and rights-based wording such as *persons with disabilities* (avoid *the disabled*, *handicapped*, or medicalized labels like *visually impaired*), *accessibility*, *reasonable accommodation*, and *universal design*.

## VitePress Conventions

Our documentation is built with **VitePress**. Follow these conventions for every page under `docs/`:

- **Frontmatter (`description`)**: Every content page must start with YAML frontmatter containing a `description` property (used for page metadata and search):

```md
---
description: This page shows you how to generate links for your surveys.
---
```

For longer descriptions, use a YAML folded scalar:

```md
---
description: >-
  A training course to help new users create a training survey and become
  familiar with Accessible Surveys.
---
```

- **Callout Containers**: Use VitePress custom containers (`info`, `tip`, `warning`, `danger`, `details`) to highlight notes, tips, or warnings. Do not use legacy GitBook `{% hint %}` Liquid tags or GitHub `> [!NOTE]` alert syntax:

```md
::: info
Only lowercase letters and numbers are allowed for identifiers.
:::
```

- **Figures and Captions**: Use `<figure>` and `<figcaption>` HTML tags for annotated screenshots and captioned images. When placing a `<figure>` inside an ordered list, indent it to align with the list item text so Markdown does not reset list numbering:

```html
<figure>
  <img src="./assets/feature/step-1.png" alt="Description of image">
  <figcaption>This is the caption for the image.</figcaption>
</figure>
```

- **Videos**: Embed YouTube videos with the `<lite-youtube>` web component, always explicitly closed (do not use legacy `<lapp-youtube>`):

```html
<lite-youtube videoid="Vu9NUKzv_LQ"></lite-youtube>
```

- **Markdown File Inclusion**: Reuse shared snippets across pages with VitePress include syntax:

```md
<!--@include: ./parts/example.md-->
```

## Rule Enforcement

Run the documentation checks from the monorepo root before committing:

- `pnpm docs:check` — runs `markdownlint-cli2` over `documentation/docs/**/*.md` (`pnpm docs:fix` auto-fixes eligible issues).
- `pnpm check:docs-links` — verifies every relative Markdown link and image under `documentation/docs/` (including `REF.md`).
- `pnpm docs:build` — builds the VitePress site and validates YAML frontmatter, includes, and VitePress routes.

The markdownlint configuration lives in `documentation/.markdownlint-cli2.jsonc` (disabling `line-length`, `no-duplicate-heading`, `no-inline-html`, `no-bare-urls`, and `headings`).
